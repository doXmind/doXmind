# DocumentStore read model splits Browsing Runtime from Full Editor Runtime

## Context

Opening a Markdown **Document** currently returns one generic `html` field and
mounts the full TipTap editor path even when the user only wants to read,
scroll, search, or navigate by outline. That single field also hides two
different meanings:

- rich editor HTML used to hydrate the **Full Editor Runtime**
- lightweight HTML suitable for the **Browsing Runtime**

Those two meanings should not share one cache. Editor HTML is lossless TipTap
state stored in the **Sidecar**. Browsing HTML is a derived, sanitized read
view of the current Markdown source.

The current implementation is also split across runtimes. The Rust sidecar
crate owns the desktop `.md + .doxmind` pair path, while the Python
`MarkdownDocumentState` path has the richer stale Sidecar, **Extras** salvage,
corrupt Sidecar, and **Block correlation** behavior. The Document Browsing
Experience needs one authoritative read contract before implementation work
continues.

This ADR resolves #78 and unblocks #79-#83.

## Decision

The authoritative **DocumentStore** read model will expose two explicit HTML
fields:

- `editorHtml` — lossless editor HTML for the **Full Editor Runtime**.
- `browsingHtml` — sanitized static HTML for the **Browsing Runtime**.

The first `browsingHtml` implementation is generated by the Rust
**DocumentStore** from the current Markdown body, not from Sidecar `html`.
It is versioned by a renderer identifier and sanitized before it crosses the
storage boundary.

For the first closed loop, `browsingHtml` is not persisted into the Sidecar.
It is derived on read. If a future cache is added, its cache key must include
both the complete Markdown hash and the browsing renderer version. This avoids
creating another ambiguous cache beside Sidecar `html`.

The existing Sidecar `html` key remains on disk for now, but its read-model
meaning is `editorHtml`. New code should not call it plain `html` at the
DocumentStore boundary.

## Read Model Shape

The read model should carry the fields below. Concrete Rust/TypeScript names
may differ, but the semantics should not.

```ts
interface DocumentReadModel {
  markdown: string;
  editorHtml: string;
  browsingHtml: string;
  meta: DocumentMeta;
  extras: unknown | null;
  outline: DocumentOutlineItem[];
  source: DocumentSourceState;
  browsingRendererVersion: string;
  correlation: CorrelationReport | null;
}

interface DocumentOutlineItem {
  id: string;
  depth: 1 | 2 | 3 | 4 | 5 | 6;
  text: string;
}

type DocumentSourceState =
  | "sidecar_fresh"
  | "sidecar_stale"
  | "sidecar_missing"
  | "sidecar_corrupt"
  | "empty";
```

`markdown` is the current Markdown body without frontmatter. The complete raw
Markdown file, including frontmatter, is still what `markdown_hash` hashes for
Sidecar freshness.

`editorHtml` is used only when the **Full Editor Runtime** activates. When the
Sidecar is fresh, `editorHtml` comes from Sidecar `html`. When the Sidecar is
missing, stale, partial, corrupt, or otherwise unusable, `editorHtml` is
rebuilt from the current Markdown body using the editor-import renderer.

`browsingHtml` is used by the default **Browsing Runtime**. It is always derived
from the current Markdown body by the browsing renderer for the current
`browsingRendererVersion`. It must not trust Sidecar `html`.

`outline` is derived from the same current Markdown body and renderer pass as
`browsingHtml`. Heading ids must be stable for one render and safe to use as DOM
anchors. If duplicate headings produce duplicate slugs, the renderer appends a
deterministic suffix.

`extras` is the resolved Extras object after stale-Sidecar salvage and
Block-correlation resolution. `null` means there is no usable Extras object.

`correlation` is the Block correlation report described by ADR-0004. `null`
means no correlator ran; an empty report means the correlator ran cleanly.

## Source State Rules

### Fresh Sidecar

When Sidecar `version` and `markdown_hash` match the current Markdown file:

- `source = "sidecar_fresh"`
- `editorHtml = sidecar.html`
- `browsingHtml` is generated from current Markdown
- `extras` comes from Sidecar Extras after Block correlation resolution
- Sidecar id wins over frontmatter id if they disagree

### Stale Sidecar

When the Sidecar exists but `version` or `markdown_hash` does not match:

- `source = "sidecar_stale"`
- Sidecar `html` is ignored
- `editorHtml` is rebuilt from current Markdown
- `browsingHtml` is generated from current Markdown
- Extras salvage runs before Block correlation
- discarded Extras slots are not exposed as live `extras`

Markdown wins over the Sidecar. This is the external-edit contract: edits made
outside doXmind must not be overwritten by stale editor HTML.

### Missing Sidecar

When no Sidecar exists:

- `source = "sidecar_missing"` for non-empty Markdown
- `editorHtml` is rebuilt from current Markdown
- `browsingHtml` is generated from current Markdown
- `extras = null` unless Block correlation creates an explicit empty structure
  for new External-reference placeholders

### Corrupt Sidecar

When the Sidecar is not parseable JSON or has a malformed top-level shape:

- `source = "sidecar_corrupt"`
- the corrupt bytes are preserved in a forensic sibling file when the platform
  implementation supports it
- Sidecar `html` and Extras are ignored because they cannot be trusted
- `editorHtml` and `browsingHtml` are rebuilt from current Markdown
- `correlation` still runs against the current Markdown body with empty Extras

The Document must remain readable. A corrupt Sidecar is a damaged cache, not a
reason to block access to the `.md` source.

### Empty Document

When the Markdown body is empty after frontmatter parsing:

- `source = "empty"`
- `markdown = ""`
- `editorHtml = ""`
- `browsingHtml = ""`
- `outline = []`

## Browsing Renderer Rules

The first renderer version should be named as a stable string, for example
`browsing-html/v1`. The exact constant can change during implementation, but
it must be exposed in the read model and included in any future cache key.

The renderer must preserve standard Markdown browsing as the product floor:

- headings, paragraphs, lists, blockquotes, task lists, tables, links, images,
  and fenced code blocks render as normal Markdown
- raw script execution and event-handler attributes are not allowed in
  `browsingHtml`
- generated ids and attributes are safe to inject into the DOM
- math auto-detection must respect ADR-0006 false-positive gates
- External-reference Custom Block placeholders remain lightweight in browsing
  output and do not eager-load PDF or Excel state

The first renderer does not need to be the final renderer for every Custom
Block. #82 owns progressive lightweight behavior for heavy Blocks.

## Python/FastAPI Fallback Boundary

The Rust DocumentStore is the authority for the read-model semantics. The
Python/FastAPI browser-dev fallback may temporarily mirror the behavior, but it
must not define different rules for:

- Sidecar version handling
- stale Sidecar detection
- Sidecar `html` trust
- corrupt Sidecar degradation
- Extras salvage
- Block correlation
- browsing renderer versioning

Until Python shells out to or binds the Rust implementation, cross-runtime
tests should pin the shared behavior at the adapter boundary.

## Consequences

- #79 should expose the read model through Tauri and the frontend storage
  adapter while keeping legacy editor callers working during migration.
- #80 should make Markdown Document opens use `browsingHtml` by default and
  avoid mounting TipTap before edit intent.
- #81 should activate the Full Editor Runtime from `editorHtml` while
  preserving scroll position.
- #82 should improve lightweight browsing output for heavy Blocks without
  changing this contract.
- #83 should measure Browsing Runtime open/paint separately from Full Editor
  Runtime activation.

Any proposal to persist `browsingHtml` in the Sidecar must first define its
cache key, invalidation, migration behavior, and relationship to Sidecar
`html`; otherwise it recreates the ambiguity this ADR removes.
