Validation date: 2026-07-21

This record pins the narrow compatibility fallback documented in the 1.8.0
release notes. It does not complete LEGACY-03 or prove that every historical
sidecar shape is recoverable.

## Sidecar behavior

Both sidecars used the version-2 Synthetic Document envelope with an
`extras.blocks.<id>.editor` payload. The PDF sidecar also contained a parsed
cache whose `sourceHash` matched the source PDF, so the 1.8.0 recovery bridge
could export it directly. The workbook sidecar did not contain `parsedCache` or
`sourceHash`; 1.8.0 therefore classified it as unsafe to apply and offered no
direct export. The isolated 1.7.8 fallback was required to recover that edit.

Opening, exporting, and quitting 1.7.8 rewrote the sidecars even when the source
Attachments were unchanged:

- Workbook sidecar: first-save SHA-256
  `4b5824f4c1cee95543c41711f286b0a0c626b19b5234d16417e41be0a764ac99`;
  final SHA-256
  `9a970ce4ff0dba4fc4379308892839cbb8407d1587998200f1a653e13b23c57a`.
- PDF sidecar: first-save SHA-256
  `2ec36494453aa9c77367dc529163e55587e6045ef528f27de1104641a7b62bae`;
  final SHA-256
  `6af40efbdfd2db9e113a73ba690ae89746171d95c1391152bb4c5d1080c3b077`.
- The old build also created `.doxmind/index.json` in the copied workspace.

The fallback is therefore safe only when the entire containing directory is
duplicated first and the old build is pointed exclusively at that duplicate.

## Scope limit

This run did not validate pre-1.7.8 `{pdf_editor, excel_editor, ...}` sidecars,
corrupt or future-version payloads, source-hash mismatch, differing main/backup
states, or `.corrupt-*` forensic copies. Those remain preserved evidence and
must not be described as covered by this fallback without representative
archived fixtures and the same packaged-app procedure.
